## 1. 项目背景与使命

### 1.1 业务背景

`ref/` 中沉淀的 9 个项目源自嵌入式 Linux 设备量产、远程运维、桌面工具等真实业务场景，但经过多年并行演化，形成了**三套能力重叠却彼此割裂**的核心组件：

| 组件 | 定位 | 通信骨干 | 进程模型 | 序列化 |
|------|------|----------|----------|--------|
| **device_framework** | 设备端点对点框架 | POSIX Socket | C/S | 自定义二进制 |
| **msgc** | 应用层消息中间件 | ZMQ + Protobuf | 多服务 + Broker | Protobuf |
| **rootfs_app** | 根文件系统服务集合 | ZMQ | 每服务独立进程 + monitor | JSON + 自研 skel |

三套组件**目标场景不同、设计哲学不同、协议不同、API 不同**，但**解决的问题高度重叠**：在嵌入式设备 + 主机 PC 之间建立可靠的双向通道。

### 1.2 项目使命

> **基于 `ref/` 中已有代码的设计经验，重新实现一个新项目 UDAF**。UDAF 不是 refactor，而是 greenfield——它**借鉴** device_framework / msgc / rootfs_app 等项目的设计经验与教训，但**不**保留它们的 API、**不**承诺向后兼容、**不**承担迁移负担。
>
> UDAF 围绕**三大并列能力**展开，**能力 A 与能力 B 共同作为能力 C 的基础**。

#### 三大能力一览

| 能力代号 | 能力名称 | 核心范围 | 在体系中的角色 |
|----------|----------|----------|----------------|
| **A** | 多协议设备/服务发现 | 双向、定期的全网状服务发现（设备 ↔ 主机 ↔ 服务）；网络参数 get/set + 设备信息 get/set | **C 的基础**（动态服务目录的来源） |
| **B** | 分布式数据流框架 | 借鉴数据流范式（节点 + 强类型输入/输出 + 声明式编排）；支持多线程 / 多进程 / **跨主机** | **C 的基础**（节点运行平台） |
| **C** | 设备 ↔ PC 通信 | 设备边界的命令执行、文件传输、心跳保活；作为 B 上的"设备侧节点"实现；通过 A 动态发现可用主机/服务 | **业务能力**（构建在 A + B 之上） |

#### 关键洞察：A 和 B 都是 C 的基础

> **每个设备都需要定期执行能力 A 的发现操作**，用于动态更新"可用主机/服务列表"。C 节点在启动时**不**依赖静态配置，而是**订阅 A 的发现结果**，动态决定连接哪个主机、调用哪个服务。

#### 能力 A 的 4 种发现场景

能力 A 必须覆盖以下 4 种网络场景（具体协议实现由架构设计决定）：

- **同一局域网内零配置发现**（设备首次接入，无需手工配置）
- **跨子网发现**（VLAN 或路由器隔离的网段）
- **广域网经已知协调者注册**（设备与主机不在同一局域网）
- **设备主动暴露自身**（设备开机即被主机感知）

#### 能力 B 的业务目标

- **极简**：核心运行时体积小、启动快、依赖少（具体数值见 §5 性能契约）
- **高效**：同主机消息延迟低（具体数值见 §5 性能契约）
- **分布式**：支持多线程 + 多进程 + **跨主机**节点调度
- **节点隔离**：单节点故障不影响其他节点

#### 能力 C 的业务目标

- 设备 ↔ PC 边界上的命令执行、文件传输、心跳保活
- C 节点通过 A 动态获取可用主机/服务列表
- C 节点通过 B 跨主机通信

### 1.3 核心价值主张

| 维度 | 价值 |
|------|------|
| **三大能力并列** | A（发现）/ B（IPC 框架）/ C（设备-PC）各司其职 |
| **A 和 B 都是 C 的基础** | A 提供"动态服务目录"，B 提供"节点运行平台" |
| **A 是双向定期发现** | 设备 ↔ 主机 ↔ 服务的全网状定期发现 |
| **B 是分布式数据流框架** | 支持多线程 + 多进程 + 多主机 |
| **借鉴 ref/ 经验** | 复用 device_framework 的协议设计、msgc 的中间件架构、rootfs_app 的服务编排经验 |
| **greenfield 心态** | 不背负历史 API 包袱 |
| **生态统一** | 单一文档、单一 CI、单一打包发布流程 |

## 2. 现状痛点分析

### 2.1 device_framework 痛点

| # | 痛点 | 详细 |
|---|------|------|
| 1 | C/C++ 双层 API 长期共存 | 上层应用仍依赖旧 C API，存在 deprecated 风险 |
| 2 | 消息头格式不可扩展 | 保留字段无明确未来用途说明 |
| 3 | 缺乏传输加密 | 仅 HMAC-SHA256 完整性校验，无加密 |
| 4 | 多线程 fork 存在 UB 隐患 | 业务线程直接 fork() 在多线程环境下未定义行为 |
| 5 | 测试覆盖不均 | 协议 + 错误码 + 加密覆盖较好，但 fork/daemon/watchdog 缺集成测试 |

### 2.2 msgc 痛点

| # | 痛点 | 详细 |
|---|------|------|
| 1 | README/CLAUDE.md 为空 | 新成员无法快速上手 |
| 2 | 测试未集成 CTest | 每个模块独立测试程序，无统一入口 |
| 3 | 第三方库路径硬编码 | 跨机器构建不可移植 |
| 4 | 错误码数量不足 | 缺少协议版本、认证、限流等 |
| 5 | 没有设备发现能力 | 依赖 device_framework 桥接设备层 |

### 2.3 rootfs_app 痛点

| # | 痛点 | 详细 |
|---|------|------|
| 1 | RPC 代码生成器单文件过大 | 缺少单元测试和模块拆分 |
| 2 | 进程隔离过细 | 多个独立服务导致监控重启链路复杂 |
| 3 | 无认证机制 | 跨主机 ZMQ 通信未加密 |
| 4 | 与 msgc 重复造轮子 | 都是 ZMQ 中间件，协议/接口各自独立 |
| 5 | RPC 消息描述格式自定义 | 不与其他项目互通 |

### 2.4 共通痛点

| # | 痛点 | 详细 |
|---|------|------|
| 1 | **协议层不互通** | 三套各自定义消息头，跨组件通信需桥接 |
| 2 | **错误码不统一** | 三套不同的错误表达 |
| 3 | **日志格式不统一** | 三种不同的日志输出 |
| 4 | **没有统一 CI** | 三个项目都没有自动化测试 |
| 5 | **没有统一指标暴露** | 都没有 metrics 暴露 |

## 3. 目标用户与典型场景

### 3.1 用户角色

| 角色 | 关注点 | 典型工作流 |
|------|--------|-----------|
| **产线工程师** | 高并发 SN 烧录、操作可追溯、错误易定位 | 扫描设备 → 选择设备 → 执行烧录 → 查看日志 |
| **嵌入式开发** | 远程调试、文件传输、命令执行、性能可观测 | SSH 替代方案：远程执行命令、上传固件、采集指标 |
| **嵌入式产品架构师** | 终端产品（GUI + 多服务）的统一架构、跨主机通信 | 设计终端产品的多服务协作框架 |
| **设备端 C 工程师** | 资源占用低、API 简洁、可静态裁剪 | 在嵌入式设备上集成 UDAF agent |
| **服务端 C++ 工程师** | 异步 I/O、消息中间件、可观测性 | 在主机端开发 UDAF 应用 |
| **运维 / SRE** | 监控指标、链路追踪、日志聚合、告警 | 部署 + 监控 + 故障定位 |
| **审计员 / 合规检查员** | 操作日志完整可追溯、保留期合规 | 导出审计报表 |

### 3.2 典型场景

#### 场景 A：产线量产 SN 烧录

```
工程师 PC（UDAF Host） ─── UDAF Protocol ──→ 设备（UDAF Device Agent）
                                            └─ fork/exec vendor_storage
```

**关键路径**：
1. 工程师打开工具，工具自动发现局域网设备
2. 工程师选择目标设备，输入 SN
3. 工具下发烧录命令，设备执行并返回结果
4. 工具自动写入审计日志（含操作员、SN、设备、时间）

**关键需求**：
- 批量发现（>100 设备）
- 并行烧录
- 二次确认弹窗（防误操作）
- 操作日志

#### 场景 B：远程运维调试

```
开发 PC（UDAF Host） ── UDAF Protocol ──→ 设备（UDAF Device Agent）
                                         ├─ fork/exec 任意命令
                                         ├─ 文件上传/下载
                                         └─ 进程/网络/服务信息采集
```

**关键路径**：开发者在 PC 端远程登录设备 shell、上传固件、采集诊断信息。

**关键需求**：交互式命令、文件分块传输、心跳保活、会话复用。

#### 场景 C：嵌入式终端产品（GUI + 多服务）

```
设备内部：
  GUI 进程 ─┐
  工作服务 ─┼─→ UDAF Host（IPC） ─→ 设备端外发（网络）
  日志服务 ─┘
```

**关键需求**：进程间/服务间通信（IPC）、跨主机通信（设备 ↔ 主机 PC）、可观测性。

#### 场景 D：多主机协作

```
设备 A ── UDAF ──→ Host A Broker ── TCP ── Host B Broker ── UDAF ──→ 设备 B
```

**关键需求**：跨主机消息路由、服务发现、健康检查。

#### 场景 E：UDAF 自身升级（运维场景）

```
管理员 PC ──→ UDAF Host ──→ 设备：检查当前版本 → 上传新版本 → 校验 → 重启 → 验证
```

**关键需求**：版本检查、断点续传、原子升级、失败回滚、远程触发。

#### 场景 F：审计与合规（合规场景）

```
合规检查员 ──→ 导出审计报表 ──→ 验证 SN 烧录追溯链 ──→ 满足行业合规要求
```

**关键需求**：审计日志完整性、不可篡改、保留期、导出格式。

**MVP 适用范围说明**：**v1.0 MVP 不满足完整合规要求**——MVP 仅记录操作员/时间戳/设备/动作/参数，本地保存 7 天，**不**提供不可篡改、长期保留（≥ 1 年）、报表导出。合规场景需等待 v1.x 不可篡改日志能力上线（详见 §10.2 P1 项）。

> 本章按 UDAF 三大能力（A / B / C）分别展开，并列出跨能力通用需求。

### 4.1 能力 A：多协议设备/服务发现（C 的基础）

#### 4.1.1 服务暴露侧（"我在这里"）

| ID | 需求 | 优先级 |

|----|------|--------|

**能力 A 的 TBD 项（阶段 2 细化）**：
- 定期扫描频率范围（业务目标：最坏情况下扫描发现时延上界 < X 秒）
- 注册表是否持久化（业务目标：设备掉电后是否需要"恢复已知主机列表"）
- A 注册表变化如何通知 C 节点（消息总线 / 自建通道）

### 4.2 能力 B：分布式数据流框架（C 的基础）

#### 4.2.0 能力 B 的业务故事

> **场景**：产线烧录时，A 发现 100 台新设备插入网络。B 框架**自动**并行启动 100 个 C 节点（每台设备一个烧录节点），实时聚合每个节点的进度到主控端。如果某台设备的节点崩溃，B 自动重启它而不影响其他 99 台设备。烧录完成后，B 自动清理所有临时节点。
>
> 这就是"分布式数据流框架"对业务的承诺：**让多个独立的处理单元协同工作，单点故障不级联，业务变更时无需重写代码**。

#### 4.2.1 框架核心能力

| ID | 需求 | 业务场景举例 | 优先级 | 状态 |
|----|------|------------|--------|------|
| F-B-01 | **数据流图运行时**（节点 + 输入/输出 + 有向无环图编排） | "100 个烧录节点并行工作，进度自动聚合" | P0 | **TBD 阶段 2** |
| F-B-02 | **声明式编排**（从配置文件加载处理流程，无需改代码） | "修改 YAML 配置即可调整烧录流程" | P0 | **TBD 阶段 2** |
| F-B-03 | **多传输场景**（同进程线程间 / 同主机跨进程 / 跨主机网络） | "GUI 进程、工作服务、设备节点各自独立但协作" | P0 | **TBD 阶段 2** |
| F-B-04 | **节点隔离**（单节点故障不级联） | "1 台设备烧录失败不影响其他 99 台" | P0 | **TBD 阶段 2** |
| F-B-05 | **动态拓扑**（根据外部信号增减节点，即"按需启动处理单元"） | "新设备上线自动启动对应节点" | P0 | **TBD 阶段 2** |
| F-B-06 | **节点生命周期管理**（启动、运行、停止、热加载） | "升级固件时不停机热加载新节点" | P0 | **TBD 阶段 2** |
| F-B-07 | **多语言节点**（首发某种主语言，绑定其他语言按需扩展） | "C++ 主节点 + Python 算法节点" | P1 | **TBD 阶段 2** |
| F-B-08 | **可观测性**（节点级 metrics + tracing + 日志） | "运维能看到每个节点的处理速率、延迟、错误率" | P1 | **TBD 阶段 2** |
| F-B-09 | **回放与录制**（节点消息录制与回放） | "复现产线问题，支持离线调试" | P2 | **TBD 阶段 2** |

**能力 B 的 TBD 项（阶段 2 必答）**：
- 节点间消息传递模型（强类型 vs 字节流）
- 节点间数据传递的零拷贝实现细节
- 跨主机节点调度的具体机制
- 节点状态持久化与崩溃恢复语义

### 4.3 能力 C：设备 ↔ PC 通信

| ID | 需求 | 优先级 | 状态 |
|----|------|--------|------|
| F-C-01 | **命令执行节点**：主机调度，设备 fork/exec 子进程，返回结果 | P0 | **TBD 阶段 2** |
| F-C-02 | **文件传输节点**：分块上传/下载，完整性校验，断点续传 | P0 | **TBD 阶段 2** |
| F-C-03 | **心跳节点**：定期发送心跳包（含资源占用信息） | P0 | **TBD 阶段 2** |
| F-C-04 | **网络信息节点**：设备端 IP/MAC/网关/DNS 等信息采集与 get/set | P0 | **TBD 阶段 2** |
| F-C-05 | **多设备并发**：主机端能同时管理 >100 设备 | P0 | **TBD 阶段 2** |
| F-C-06 | **设备监控**：心跳聚合、离线检测、自动重连 | P0 | **TBD 阶段 2** |
| F-C-07 | **命令模板引擎**：支持占位符替换 + 安全过滤 | P0 | **TBD 阶段 2** |
| F-C-08 | **设备端节点**：设备端作为远程节点运行 | P0 | **TBD 阶段 2** |
| F-C-09 | **PC 工具**：提供命令行工具集 | P0 | **TBD 阶段 2** |

**能力 C 与能力 A 的关系**：
- C 节点启动时**不**读静态配置，而是**订阅能力 A 的服务注册表**
- 当 A 通知"新主机上线 / 新服务可用"时，C 节点**自动**建立连接 / 触发调度
- 当 A 通知"主机/服务下线"时，C 节点**自动**断开 / 切换备选

**能力 C 与能力 B 的关系**：
- C 节点是 B 框架的标准节点
- C 节点通过 B 的跨主机调度能力运行在设备端
- C 节点**复用** B 的传输、可观测性、热加载等基础设施

**能力 C 的 TBD 项（阶段 2 必答）**：
- C 节点的"消息契约"格式
- 设备端身份认证机制
- 加密通道的实现边界
- C 节点如何根据 A 注册表自动决定连接目标（负载均衡 / 就近 / 白名单）

### 4.4 跨能力通用需求

### 5.6 消息中间件语义契约

> 本节是阶段 2 中间件选型（ZMQ / Aeron / Kafka / 自研）的第一性约束。

| 语义维度 | 业务要求 |
|----------|----------|
| **顺序保证** | 同会话（同一源/目的对）内消息严格保序；跨会话无顺序保证；Broker / 节点切换期间允许短暂乱序（≤ 100 条） |
| **持久化（v1.0）** | 设备端消息**不持久化**（接受崩溃丢失，依赖业务侧幂等）；主机端消息按需可选持久化 |
| **持久化（v1.x）** | 主机端持久化（崩溃后未投递消息保留 ≥ 24 小时）；持久化层独立于消息中间件 |
| **投递语义** | **至少一次**（业务侧需幂等处理）；v1.x 可选"恰好一次"模式（业务侧注明需求） |
| **消息优先级** | 三级：心跳 / 控制 / 业务数据；高优先级消息可抢占低优先级队列 |
| **消息大小** | 默认 4KB，最大 1MB（超出拒绝接收并告警） |
| **背压策略** | 队列满时高优先级消息**强制投递**（触发反压信号给上游）；低优先级消息丢弃并告警 |

## 7. 异常路径与降级策略

> 本章列出关键异常场景的处理策略。详细实现细节在架构设计阶段补充。

### 7.1 协议与兼容

| 异常场景 | 处理策略 |
|----------|----------|
| **旧 ref/ 设备（DFRM 协议）共存** | 提供一次性导入工具，不在协议层兼容 |
| **跨主机协议版本不一致** | 握手阶段协商版本，降级到共同支持的最高版本 |
| **加密协议不可用** | 生产环境：拒绝连接；开发环境：可降级到明文（需显式启用） |

### 7.2 认证失败

| 异常场景 | 处理策略 |
|----------|----------|
| **证书过期** | 设备进入"待重新认证"状态，仅响应发现请求，拒绝业务命令 |
| **PSK 错配** | 主机侧记录失败次数；超过阈值后暂时锁定（防暴力破解） |
| **白名单为空** | 设备进入"锁定"状态，仅响应主机侧的"重新配对"请求 |
| **证书链校验失败（v1.x PKI）** | 拒绝连接；记录详细错误（哪个环节失败：chain / signature / expiration）；主机侧告警 |
| **CA 不可达（v1.x PKI）** | 启动时使用本地缓存 CA 证书；运行时降级到"仅信任已缓存 CA 颁发的证书"模式 |
| **CRL 检查失败 / CRL 过期（v1.x PKI）** | 拒绝连接；记录告警；降级到"上次已知未撤销"模式（业务可选） |
| **证书撤销（v1.x PKI）** | 强制立即吊销连接；保留撤销记录用于审计；触发设备重新认证流程 |
| **协议版本协商失败** | 拒绝连接；记录两端协议版本；触发手动或自动升级 |

### 7.3 资源耗尽

| 异常场景 | 处理策略 |
|----------|----------|
| **设备端内存不足** | 调度器停止低优先级节点；记录告警 |
| **CPU 过载** | 调度器拒绝新节点注册；通知主机端 |
| **磁盘空间不足** | 日志写入失败 → 降级到仅控制台输出；上传文件失败 → 通知主机 |
| **fd 耗尽** | 调度器拒绝新连接；触发 GC 释放空闲 fd |

### 7.4 时钟与时间

| 异常场景 | 处理策略 |
|----------|----------|
| **NTP 不可用 / 时钟漂移** | 心跳超时容忍度放宽（如 ±20%）；审计日志标注时钟状态 |
| **时钟回拨** | 不影响功能（使用单调时钟计算超时）；日志记录回拨事件 |

### 7.5 网络异常

| 异常场景 | 处理策略 |
|----------|----------|
| **网络分区** | 节点标记离线；分区恢复后自动重连 + 同步状态 |
| **Broker 宕机** | 客户端切换备选 Broker；记录告警 |
| **带宽饱和** | 心跳降级（延长周期，从 1Hz → 0.1Hz）；业务消息优先；触发反压信号 |
| **DNS 不可用** | 缓存已知主机 IP；新主机发现能力临时降级 |

### 7.6 运行环境异常

| 异常场景 | 处理策略 |
|----------|----------|
| **电源故障 / 突然断电** | 设备端关键状态持久化（write-ahead log，**写入范围仅注册表 + 未确认业务消息**，不含审计日志）；启动时检测上次异常退出并恢复；**崩溃恢复时延 ≤ 5 秒** |
| **磁盘 I/O 错误** | 仅记录告警 + 降级到内存缓存（**缓存最长保留 60 秒或 1000 条**，超时或超额丢弃）；不阻塞业务 |
| **磁盘空间不足** | 日志降级（仅控制台）；审计日志压缩归档；上传文件失败时通知主机 |
| **外部依赖不可用（CA / 配置中心 / NTP）** | 启动时使用本地缓存配置；运行时降级到只读模式 |
| **加密密钥泄露 / 撤销** | 证书撤销列表（CRL）本地缓存；撤销后强制重新认证 |
| **整进程崩溃（不仅是节点）** | 由 watchdog 进程拉起；记录崩溃现场（coredump + 最近 100 条日志）；**同一进程 60 秒内连续崩溃 3 次后停止自动重启并告警** |
| **恶意大消息（超过协议限制）** | 拒绝接收；记录告警；触发临时黑名单 |
| **WAL 磁盘满** | 停止写入新 WAL 条目但保留旧条目；告警；启动时优先回放 |
| **watchdog 自身崩溃** | 由 systemd / init 系统接管拉起；watchdog 自身崩溃时降级到"节点级自愈"模式 |

### 7.7 长期稳定性

| 异常场景 | 处理策略 |
|----------|----------|
| **长期内存泄漏（30 天+）** | 周期性内存自检；RSS 增长超阈值主动重启；崩溃前 dump heap snapshot |
| **时钟漂移长期累积** | NTP 长期不可用时业务时钟容忍漂移 ±5%；审计日志标注时钟状态 |
| **CPU 长期满载** | 触发自适应降级（心跳降级 + 关闭非关键 metrics）；记录告警 |

### 7.8 核心能力降级路径

| 能力 | 降级触发条件 | 降级模式 | 恢复条件 |
|------|------------|----------|----------|
| **A（发现）** | 广播/多播被禁用 | 仅用 TCP 注册模式 | 网络策略恢复 |
| **B（数据流）** | 进程隔离异常或共享资源不足 | 同进程单线程模式 | 资源恢复 + 自动升级 |
| **C（设备-PC）** | 加密握手失败或证书过期 | 禁止远程命令，仅响应发现请求 | 重新认证成功 |

**§7 与 §5 可靠性契约联动说明**：

- §5.2 "设备断连自动重连 主机端 3 秒内检测"：主机端立即检测 + 主动重连，不等心跳超时
- §7.5 "心跳降级（延长周期）"：仅在带宽饱和时触发，与 §5.2 "3 次心跳丢失才标记离线"叠加——降级期间用更长超时窗口
- §7.7 "长期内存泄漏 → 主动重启"：与 §5.2 "节点崩溃恢复" 复用同一调度机制

- **H-01a 破坏**（产线 PC 与设备不同子网）：v1.0 仅支持同子网；远程产线场景推迟到 v1.x

- **H-04 破坏**（用户不接受 greenfield）：v1.0 提前冻结 API 并提供迁移工具

### 10.3 PSK → PKI 迁移路径

**v1.0 阶段（临时方案）**：
- 使用 PSK（Pre-Shared Key）作为认证基础
- 通过 USB / 串口 / 一次性配置接口注入 PSK
- 适用：产线集中配对、设备数量 < 100 的小规模场景

**v1.x 阶段（目标方案）**：
- 引入 PKI 证书管理子系统
- 设备首次接入由 CA 颁发 X.509 证书
- 支持证书轮换（自动 / 手动）
- 适用：大规模部署、多主机联邦、安全合规要求高的场景

**兼容性策略**：
- v1.x 同时支持 PSK 与 PKI 两种模式（通过配置切换）
- 已有 PSK 设备可升级到 PKI（无需重烧固件）
- v2.0 计划弃用 PSK（提前 6 个月公告）
