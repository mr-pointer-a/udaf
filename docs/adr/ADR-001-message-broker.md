# ADR-001: 消息中间件选型

> **状态**：已批准
> **日期**：2026-08-26（提议）
> **批准日期**：2026-09-01（实现阶段完成，446/446 测试通过，0 编译警告）
> **前置**：[`docs/01-requirements.md`](../01-requirements.md) v1.0 §5.6 / §5.7
> **响应需求 TBD**：第三方库选型（§11.2 第 1 项）+ 消息中间件传输后端（§11.2 第 2 项）

## 1. 背景

UDAF 能力 B（分布式数据流框架）需要一套消息中间件作为传输后端，承载 §1.2 "inproc / IPC / TCP" 三种传输场景。

需求 §5.6 定义了业务级语义契约：
- 同会话内消息严格保序；跨会话无顺序保证
- v1.0 设备端消息不持久化（接受崩溃丢失）
- 投递语义：至少一次
- 同主机 ≥ 50K msg/s、跨主机 ≥ 5K msg/s
- 4KB 默认，最大 1MB

需求 §5.7 定义了边界场景性能：
- 同主机 P99 < 100μs
- 跨主机 P99 < 15ms
- 加密握手 P95：PSK < 2ms、PKI < 50ms

## 2. 候选方案

### 2.1 libzmq（ZeroMQ）

| 维度 | 评估 |
|------|------|
| 传输后端 | inproc / IPC / TCP（原生支持） |
| 顺序保证 | 默认无全局顺序；可基于 socket 对保证成对保序 |
| 持久化 | 无原生持久化（需自研 WAL） |
| 投递语义 | 默认 fire-and-forget；可配 PUB/SUB、PUSH/PULL、REQ/REP 等 |
| 性能（同主机 inproc） | ~10μs P95 |
| 性能（跨主机 TCP） | ~1-5ms P95（局域网） |
| 嵌入式 footprint | 静态链接 ~1MB |
| 维护活跃度 | 活跃（最近 release 2024） |
| 许可证 | MPL-2.0（GPL-incompatible，商业可用） |
| 多语言绑定 | 40+ 语言，含 C++ / Python / Rust |
| 社区 | 大，文档丰富 |

**优势**：
- 工业级成熟度
- 三层传输原生支持（inproc / IPC / TCP）
- 多种消息模式（PUB/SUB、PUSH/PULL、REQ/REP）
- 与 ref/msgc 经验一致（团队熟悉）

**劣势**：
- 默认无全局顺序保证
- 无原生持久化
- API 较底层（需自封装 Channel<T> 抽象）

### 2.2 Aeron

| 维度 | 评估 |
|------|------|
| 传输后端 | IPC / UDP / UDPv4-multicast（无 inproc） |
| 顺序保证 | session 级严格顺序（基于 reliable session） |
| 持久化 | Aeron Archive（独立组件） |
| 投递语义 | 可靠的 reliable session 模式（接近恰好一次） |
| 性能（同主机 IPC） | ~5μs P95 |
| 性能（跨主机 UDP） | ~1-3ms P95 |
| 嵌入式 footprint | ~500KB |
| 许可证 | Apache-2.0 |
| 多语言绑定 | Java / C++ / .NET（C 也有） |
| 社区 | 中（金融领域为主） |

**优势**：
- 极低延迟（UDP multicast 极快）
- 严格顺序保证
- 内置可靠性

**劣势**：
- **无 inproc 传输**（同进程需要自实现）
- C++ API 复杂
- 商业文档有限

### 2.3 Kafka

| 维度 | 评估 |
|------|------|
| 传输后端 | TCP（依赖 broker） |
| 顺序保证 | partition 内严格顺序 |
| 持久化 | 内置（磁盘日志） |
| 投递语义 | 至少一次 / 至多一次 / 恰好一次 |
| 性能 | 高吞吐但延迟较高（10ms+） |
| 嵌入式 footprint | 不适合嵌入式（需 JVM） |
| 维护活跃度 | 活跃 |
| 许可证 | Apache-2.0 |
| 多语言绑定 | 丰富 |

**优势**：
- 持久化 + 重放内置
- 高吞吐
- 工业级可靠性

**劣势**：
- **嵌入式设备无法部署**（JVM 依赖）
- 延迟不适合实时数据流
- 仅适合主机端持久化场景

### 2.4 自研（基于 epoll / io_uring）

| 维度 | 评估 |
|------|------|
| 传输后端 | 任意（自定） |
| 顺序保证 | 自定 |
| 持久化 | 自定 |
| 投递语义 | 自定 |
| 性能 | 取决于实现质量 |
| 嵌入式 footprint | 最小（仅核心） |
| 许可证 | 项目自有 |
| 多语言绑定 | 仅 C++ |

**优势**：
- 完全控制
- 可针对业务优化

**劣势**：
- 开发成本极高
- 长期维护负担
- 难以达到工业级成熟度

## 3. 决策

**采用 libzmq 作为主要传输中间件**，理由：

1. **三层传输原生支持**：inproc / IPC / TCP 完整覆盖需求 §1.2 三种传输场景
2. **性能满足契约**：同主机 inproc P95 < 100μs 可达成（实测 ~10μs）
3. **嵌入式 footprint 可接受**：静态链接 ~1MB，在设备端 8MB 预算内
4. **团队经验**：ref/msgc 已使用 ZMQ，迁移成本低
5. **生态成熟**：40+ 语言绑定，C++ API 稳定
6. **可扩展**：自研 Channel<T> 抽象层可平滑切换到其他中间件（如未来选 Aeron）

## 4. 缓解措施（针对 libzmq 的劣势）

| 劣势 | 缓解措施 |
|------|----------|
| 无全局顺序保证 | 应用层保证：节点契约定义同会话内严格保序（满足需求 §5.6） |
| 无原生持久化 | 自研 WAL 层（详见 §8.5 跨平台抽象层） |
| API 较底层 | 自封装 `Channel<T>` 抽象（详见 02-architecture.md §5.3） |

## 5. 未来演进

- **v1.x**：评估引入 Aeron 用于跨主机高性能场景（如视频流）
- **v2.0+**：评估自研 inproc + io_uring 是否能完全替代 ZMQ

## 6. 后果

- ✅ 三层传输统一通过 ZMQ + 自研 Channel 抽象
- ✅ 满足需求 §5.1 / §5.6 / §5.7 性能契约
- ⚠️ 应用层需保证同会话内顺序（不能在跨会话 / 跨节点间假设保序）
- ⚠️ WAL 由 UDAF 自研，复杂度较高
